## Claude

The core insight is sound, and it maps cleanly to how good software is actually built. Here's what holds up, what doesn't, and what's genuinely novel about framing it recursively:

**What's right:**

The self-similarity is the key observation. The same decompose → implement → compose loop applies identically at every scale: app, feature, module, function. That's not just a process metaphor — it means the same cognitive algorithm and the same tooling can work at every level of the hierarchy. You're not switching between "architecture mode" and "coding mode" — it's the same move, recursively applied.

Depth-first bottom-up also solves the dependency ordering problem automatically. If you've decomposed correctly, a leaf node has no incomplete dependencies by definition. You never block on something that isn't done yet.

**The hard part is the decomposition, not the traversal:**

The traversal is nearly mechanical once the tree exists. The intellectual work is: (1) deciding what the right decomposition is, and (2) knowing when you've hit a leaf. "Atomic" isn't a fixed threshold — it's domain-specific and judgment-dependent. A unit is atomic when it's implementable without any other incomplete sibling node. That definition is recursive too, which is clean.

**Where the tree model strains:**

Real systems are DAGs, not trees. Auth, logging, error handling, shared types — these are cross-cutting concerns that multiple subtrees depend on. The tree model handles this if you declare them as shared leaf nodes that get implemented first, but it requires acknowledging that the decomposition isn't purely hierarchical.

The other tension: the tree changes as you implement it. A node that looked atomic on day one often needs to be decomposed further when you actually sit down to implement it. The tree is a hypothesis, progressively refined through implementation.

**What's genuinely new in this framing:**

Most PRDs are narratives. What you're describing treats the PRD itself as the WBS — the spec *is* the decomposition, not a separate artifact. That collapses the translation layer between "what we're building" and "the work to do it." The spec node and the implementation artifact are in 1:1 correspondence.

This also makes progress objective. Percentage of leaf nodes implemented = percentage complete. No more "60% done" ambiguity.

**For AI-assisted development specifically:**

This framing is particularly powerful here. An LLM agent can hold one subtree in context, implement its leaves, and hand the composed result back up. A parent agent coordinates without needing to know the implementation details of child subtrees. Each subtask is bounded, the interface contracts are defined by the parent node, and error recovery is localized. This is structurally what multi-agent coding systems are converging toward — your framing gives it a clean theoretical basis.

**The one thing to name explicitly:**

The PRD/WBS decomposition step is where the expertise lives. If the decomposition is wrong — wrong abstractions, wrong level of granularity, wrong interface contracts between nodes — the bottom-up implementation will produce leaf nodes that don't compose. The recursive process surfaces bad decompositions faster than waterfall would, but it doesn't prevent them.

Bottom line: this is a coherent and implementable model. The recursive framing isn't just an analogy — it actually changes how you'd design tooling (same loop at every scale), measure progress (leaf node count), and structure AI assistance (bounded subtrees). The main engineering work is specifying what "atomic" means for your domain and handling the DAG reality of shared dependencies.

# capture-chat v1.0

## Purpose

Exports a Cowork/Claude Code session into a clean, structured format for later
use or immediate vault ingest. This skill is also the **canonical source** for
`export-conversation.py` — the script deployed to every ALV vault root at
scaffold time.

---

## Two Modes

### Capture (conversation only)

- **Output:** a single `.md` file with all human and assistant turns
- **Use when:** the conversation itself is the artifact — design discussions,
  strategy sessions, Q&A, decisions made in chat
- **Filename:** `YYYY-MM-DD-conversation-export.md`
- **Run:** `python3 export-conversation.py --out <destination>`

### Export (conversation + artifacts)

- **Output:** a folder containing `conversation.md` + `artifacts/` subdirectory
  with copies of every file written during the session
- **Use when:** the session produced code, documents, or other files you want
  to preserve alongside the conversation record
- **Folder:** `YYYY-MM-DD-session-export/`
- **Run:** `python3 export-conversation.py --artifacts --out <destination>`

**When in doubt, capture.** Export adds artifact copying — if you only care
about the conversation, capture is sufficient and simpler.

---

## Running the Script

The script lives in the vault root as `export-conversation.py`. Run it from the
vault root directory.

```bash
# Capture mode (conversation only) — save to vault inbox for ingest
python3 export-conversation.py --out inbox/

# Export mode (conversation + artifacts) — save to vault inbox for ingest
python3 export-conversation.py --artifacts --out inbox/

# Capture to a specific file
python3 export-conversation.py --out my-session-notes.md

# Export to Desktop
python3 export-conversation.py --artifacts --out ~/Desktop/

# Explicit JSONL path (override auto-detect)
python3 export-conversation.py path/to/session.jsonl --out inbox/

# Check script version
python3 export-conversation.py --version
```

**Auto-detect limitation:** without an explicit JSONL path, the script finds
the most recently modified `.jsonl` under `.claude/projects/`. This is usually
correct for an active session but may pick the wrong file if multiple sessions
are open. Pass the path explicitly when in doubt.

---

## How the Script Works

The script reads the session JSONL, filtering to:

- **Human turns:** `type == "user"`, `userType == "external"`, `isSidechain == false`
- **Assistant turns:** `type == "assistant"`, `isSidechain == false`, `type == "text"` content blocks only (skips tool_use, thinking, reasoning)

In `--artifacts` mode, it additionally scans assistant messages for `tool_use`
blocks with `name == "Write"`, collects all `file_path` values, and copies any
files that still exist on disk into the `artifacts/` subfolder of the output
folder.

2. `~/Desktop/` — save to Desktop for manual access
3. Custom path — user specifies
